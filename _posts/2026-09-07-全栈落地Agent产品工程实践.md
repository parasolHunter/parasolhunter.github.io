业务 Agent 面试若只有理论，很容易被追问「你线上怎么接」。本文以 **Nest + React 全栈 SaaS** 里接 LangChain 助手的通用模式为例，讲 Tool 边界、记忆分层、限流队列 — 不绑定单一产品名，方便你对照自己的仓库口述。

### 一、架构一句话

```text
React 对话 UI → POST /api/agent/chat
    → Nest Guard（登录、限流）
    → LangChain Agent（本机 Ollama / 云端 OpenRouter）
    → @tool 仅调内部 Service（解析、配额、套餐）
    → 自定义事件回灌前端向导（解析结果填表，不单开聊天页）
```

**原则：模型不直连 Spotify / 支付 / 数据库，只调已校验的业务 API。**

### 二、为什么不让模型直连第三方

| 风险 | 直连后果 | Tool 封装后 |
|------|----------|-------------|
| 越权 | 用错用户 token | Service 层注入 session |
| 幻觉 URL | 编造歌单链接 | `fetchByUrl` 校验格式 |
| 额度绕过 | 无限解析 | Redis 计数 + 套餐校验 |
| 密钥泄露 | Prompt 夹带 secret | 密钥只在服务端 |

### 三、记忆分层（诚实对标缺口）

| 类型 | 典型实现 | 面试怎么说 |
|------|----------|------------|
| 短记忆 | 最近 N 轮对话 | 「对话轮次在窗内」 |
| 工作记忆 | 本轮 tool scratchpad | LangChain Agent 默认 |
| 长记忆 | 摘要或向量用户画像 | 「用户级长期记忆在路线图」 |

设计客服级 Agent 时要能讲：**截断策略、超限摘要、PII 不进长期库、embedding 成本**。

### 四、Nest 工程清单

- **模块边界** — `AgentModule` 依赖 `PlaylistModule`、`BillingModule`，Tool 是薄适配层。
- **DTO 校验** — `class-validator` 校验 chat 入参，防超大 context。
- **限流** — Redis：解析 30 次/分钟·IP，迁移 10 次/小时·用户（示例口径）。
- **异步任务** — 长任务入 BullMQ，进度 Redis、终态 MySQL，关页不丢。
- **支付** — Stripe Webhook 用 **raw body** 验签，JSON 中间件先 parse 会失败。
- **Token 存储** — refresh token AES-GCM，不进日志。

### 五、前端：Agent 不是孤岛

- 解析成功 → 自定义 DOM 事件 / store，**结果灌进向导第二步**，用户无需复制粘贴。
- 流式可选 SSE；进度展示 Polling vs SSE 的权衡要能讲。
- i18n、OAuth 回调、Hash 路由 — 体现「全栈 Agent」是产品能力，不是 API 玩具。

### 六、性能与诚实表述

若项目有「串行 delay、文本匹配、大 chunk」等审计结论，面试 **讲方案与优先级（P0 并发池、P1 ISRC、P2 SSE）**，不要说「已全量优化完」。工程成熟度体现在 **先量化再立项**。

### 七、面试 30 秒版本

> 我做的是把 Agent 接到真实 SaaS 闭环：服务端 Tool、配额与 OAuth 在 Nest 收口，前端把解析结果接进向导。模型负责理解与选工具，业务正确性由 Service 与审核规则保证。
