把 Agent 接到真实 SaaS 产品里，和做一个聊天 Demo 完全是两回事。本文以 **Nest + React 全栈** 里接入 LangChain 助手的模式为例，记录 Tool 边界、记忆分层、限流队列等工程决策 — 这也是我独立全栈项目里的核心架构思路。

### 一、架构一句话

```text
React 对话 UI → POST /api/agent/chat
    → Nest Guard（登录、限流）
    → LangChain Agent（本机 Ollama / 云端 OpenRouter）
    → @tool 仅调内部 Service（解析、配额、套餐）
    → 自定义事件回灌前端向导（解析结果填表，不单开聊天页）
```

**原则：模型不直连第三方 API / 支付 / 数据库，只调已校验的业务 Service。**

### 二、为什么不让模型直连第三方

| 风险 | 直连后果 | Tool 封装后 |
|------|----------|-------------|
| 越权 | 用错用户 token | Service 层注入 session |
| 幻觉 URL | 编造无效链接 | `fetchByUrl` 校验格式 |
| 额度绕过 | 无限调用 | Redis 计数 + 套餐校验 |
| 密钥泄露 | Prompt 夹带 secret | 密钥只在服务端 |

### 三、记忆分层

| 类型 | 典型实现 | 当前策略 |
|------|----------|----------|
| 短记忆 | 最近 N 轮对话 | 对话轮次在上下文窗内 |
| 工作记忆 | 本轮 tool scratchpad | LangChain Agent 默认 |
| 长记忆 | 摘要或向量用户画像 | 用户级长期记忆在路线图 |

设计面向业务的 Agent 时，需要提前考虑：**截断策略、超限摘要、PII 不进长期库、embedding 成本**。

### 四、Nest 工程清单

- **模块边界** — `AgentModule` 依赖业务 Module，Tool 是薄适配层。
- **DTO 校验** — `class-validator` 校验 chat 入参，防超大 context。
- **限流** — Redis：解析按 IP、迁移按用户分级限流。
- **异步任务** — 长任务入 BullMQ，进度 Redis、终态 MySQL，关页不丢。
- **支付** — Stripe Webhook 用 **raw body** 验签，JSON 中间件先 parse 会失败。
- **Token 存储** — refresh token AES-GCM，不进日志。

### 五、前端：Agent 不是孤岛

- 解析成功 → 自定义事件 / store，**结果灌进向导下一步**，用户无需复制粘贴。
- 流式用 SSE；进度展示在 Polling 与 SSE 之间按场景选型。
- i18n、OAuth 回调、Hash 路由 — Agent 是产品能力的一部分，不是独立聊天页。

### 六、性能：先量化再立项

遇到「串行 delay、文本匹配、大 chunk」等瓶颈时，我的习惯是 **先审计再排优先级**（P0 并发池、P1 精确匹配与缓存、P2 SSE），而不是宣称「已全量优化」。工程成熟度体现在数据驱动的迭代。

### 七、小结

> Agent 接到真实 SaaS 闭环：服务端 Tool、配额与 OAuth 在 Nest 收口，前端把解析结果接进主流程。模型负责理解与选工具，业务正确性由 Service 与审核规则保证。
