RAG 是 Agent 体系的「知识底座」。工程上真正决定质量的，不是会不会调 embedding API，而是：**分块是否合理、检索准不准、没有证据时敢不敢拒答、效果怎么量化**。本文按链路拆解，并结合跨境物流 / 研发知识库场景记录实践要点。

### 一、标准链路

```text
原始文档 → 清洗去重 → 分块(Chunking) → Embedding
    → 向量索引 + BM25 倒排 → 混合召回 TopK
    → Reranker 精排 → 上下文拼装（带来源元数据）
    → LLM 生成（强制引用）→ 拒答/审核 → 反馈回流评测集
```

### 二、分块：别从固定 512 字符开始

| 文档类型 | 分块策略 | 元数据示例 |
|----------|----------|------------|
| PRD / 规则文档 | 按标题、段落、表格边界 | 模块、版本、权限标签 |
| 接口文档 | 按接口 + 字段说明子块 | `path`、`error_code` |
| 长文 | 语义块 + overlap | 章节路径 breadcrumb |

物流场景例子：「账号绑定」「运费试算」「沙特短地址」应是天然一级块；用户问「沙特为什么填短地址」时，应命中规则块而非整份 PRD。

### 三、为什么默认混合检索

| 方式 | 强项 | 弱项 |
|------|------|------|
| 向量检索 | 同义表达、自然语言问法 | 订单号、接口名、错误码易漏 |
| BM25 / 关键词 | 精确 token、专有名词 | 不懂语义近义 |
| 混合 + Rerank | 兼顾召回与精排质量 | 实现与算力成本更高 |

企业知识库里，用户既问自然语言，也贴 `IOSS`、`TRACK_SHIPMENT`、错误码 — **默认向量 + BM25，再 Rerank**；同时做权限与文档版本过滤。

### 四、幻觉治理：设定可交付的工程目标

不要承诺「零幻觉」。可交付目标是：

1. **检索分数低于阈值 → 明确拒答**（「现有资料未找到依据」）。
2. **回答必须附来源**（文档名、章节、链接）。
3. **Prompt 约束**：仅基于给定上下文，禁止补充未检索到的业务规则。
4. **关键字段二次校验** — 金额、地址、合规字段走规则引擎或人工。
5. **结构化输出** — 结论 / 依据 / 待确认项分开。

### 五、向量库选型参考

| 产品 | 定位 | 适用场景 |
|------|------|----------|
| Qdrant | 生产向量库，过滤与运维友好 | 中台 RAG、权限过滤 |
| Milvus | 大规模、集群运维导向 | 超大规模向量场景 |
| Chroma | 本地原型、轻量 | PoC 与本地实验 |

### 六、评测三层

1. **检索层** — Recall@K、MRR、是否命中文档。
2. **生成层** — 答案正确性、引用一致性、拒答正确率。
3. **体验层** — 首字延迟、用户追问率、人工转接率。

评测集必须来自**脱敏真实业务问题**，按意图分层，不能只用模型自生成题。

### 七、参考架构：带长期记忆的智能客服

以物流场景为例，比空泛的「客服 Bot」更容易落地：

```text
1. 接入：鉴权、会话 thread_id、SSE 流式
2. 规划：意图分类 — FAQ 走 RAG，改单走 Tool + 审核 Agent
3. 记忆：短窗 + 用户画像向量；PII 不进长期库
4. 工具：查运费、查轨迹 — 超时熔断、幂等键
5. 评测：完成率、工具正确率、幻觉、耗时、成本
6. 降级：检索空 → 拒答；模型挂 → 规则回复或人工
```

### 八、RAG vs 微调

**频繁变的业务规则、项目档案 → RAG（可追溯、可热更新）；稳定的风格/格式/分类 → 才考虑微调。** 物流知识库默认先 RAG。
