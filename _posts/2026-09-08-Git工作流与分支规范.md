团队规模上来之后，分支策略比「每人一套习惯」更重要。本文整理我在 B 端项目里长期使用的一套 **GitLab Flow 变体**：覆盖开发、集成测试、灰度、上线与热修复，并附带分支命名与 Commit 规范。不涉及具体 CI 平台，流程可直接映射到 GitLab / GitHub / 自建 Git 服务。

### 一、分支角色一览

| 分支 | 来源 | 用途 | 是否允许直接 push |
|------|------|------|-------------------|
| `master` | — | 生产基线，与线上一致 | 否（保护分支） |
| `develop` | `master` | 集成测试 / SIT 环境 | 否 |
| `feature/*` | `master` | 功能开发 | 开发者 push，MR 合并 |
| `release/*` | `master` | 灰度 / UAT | 否（MR 合并） |
| `hotfix/*` | `master` | 线上缺陷紧急修复 | MR 合并 |

**原则**：`master` 与 `release/*` 为上游保护分支，功能代码通过 Merge Request 进入，避免直接在主干上开发。

### 二、功能开发阶段（Dev → QA）

```text
1. 从最新 master 检出 feature 分支
   git checkout master && git pull
   git checkout -b feature/迭代代号

2. 日常开发：每天 rebase/merge 最新 master，减少后期冲突
   git fetch origin && git merge origin/master

3. 模块转测前，从 master 更新 develop（或由 CI 自动同步）
   git checkout develop && git pull

4. 将 feature 合并进 develop，触发测试环境部署
   git checkout develop
   git merge feature/迭代代号
   git push origin develop
```

**注意**

- 编码只在对应的 `feature/迭代代号` 上进行。
- `develop` 作为 QA 集成环境，**不要把 develop 的变更反向 merge 到 feature**，否则会把未验收代码带进功能分支。

### 三、灰度与上线（UAT → Release）

```text
1. 从最新 master 检出 release 分支
   git checkout -b release/uat-迭代代号 master

2. feature 开发完成 → 提 MR：feature → release(uat)

3. 灰度环境验证通过后，提 MR：release(uat) → master

4. 合并 master 后打 tag
   git tag -a v1.0.0.20220909 -m "release notes"
   git push origin --tags

5. 清理已合并的 feature / release 分支（本地 + 远程）
```

### 四、线上热修复（Hotfix）

```text
1. 从 master 检出 hotfix
   git checkout -b hotfix/缺陷代号 master

2. 修复完成 → 走 QA / 灰度流程（与功能发布相同）

3. 验收后 MR：release 或 hotfix → master，打 tag

4. 同步 cherry-pick 或 merge 回 develop，避免下版本回归
```

### 五、分支命名规范

| 类型 | 规则 | 示例 |
|------|------|------|
| 迭代 | 以版本特性命名 | `feature/vip_v0509` |
| AB 实验 | 加版本前缀 | `feature/versionA_vip_v0509` |
| 缺陷 | 以问题域命名 | `hotfix/login-error` |
| 上线 tag | 主.子.修订.日期 | `v1.0.0.20220909` |

**语义化版本递增**

- **主版本**：不兼容的 API 变更
- **次版本**：向下兼容的功能新增
- **修订号**：向下兼容的问题修复
- **日期 / 构建号**：按团队约定附加，便于追溯发版记录

**阶段标记（可选）**：Alpha（内测）→ Beta（公测）→ RC（候选）→ Release（正式）。

### 六、Commit 信息规范（Conventional Commits）

```bash
git commit -m "<type>[optional scope]: <description>"
# 示例
git commit -m "feat(auth): 支持 OAuth 回调"
git commit -m "fix(billing): 修复金额精度丢失"
```

| type | 含义 |
|------|------|
| feat | 新功能 |
| fix | 缺陷修复 |
| docs | 文档 |
| style | 格式（不影响逻辑） |
| refactor | 重构 |
| perf | 性能 |
| test | 测试 |
| build | 构建系统 |
| ci | CI 配置 |
| chore | 杂项 |
| revert | 回滚 |

`scope` 可选，表示影响模块，如 `views`、`utils`、`api`。`description` 一句话说清「做了什么」，冒号后留空格。

### 七、与 IDE 的配合

日常高频操作可以概括为：**fetch → checkout → add → commit → pull --rebase → push → MR**。

- 切换分支前有未提交改动：用 `git stash` / `git stash pop`，避免污染其他分支。
- 冲突优先在本地 rebase 阶段解决，再 push，减少 MR 里的合并提交噪音。
