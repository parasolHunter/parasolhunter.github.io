除了业务 Agent，「研发 Agent」和「多编码 Agent 协同」正在成为团队工程化的新常态：Cursor 子 Agent、代码评审 Bot、Figma MCP — 本质都是 **在软件交付流程里编排角色与 SOP**。本文把我在团队侧的实践抽象成可复用的编排思想，适用于前端架构师带团队落地 AI 辅助研发。

### 一、研发 Agent 团队 vs 业务 Agent 团队

| 维度 | 业务 Agent（客服/运营） | 编码 Agent（研发效能） |
|------|-------------------------|------------------------|
| 目标 | 完成业务任务、可追溯答复 | 改代码、走 CI、对齐设计 |
| 风险 | 幻觉答错、越权调工具 | 误删文件、乱改接口、泄露密钥 |
| 编排 | 规划/检索/审核 | 分析/实现/测试/评审 分工 |
| 协议 | REST + 业务 Tool | Git + MCP + CLI |

### 二、编码协同的典型角色 SOP

不必机械对应「四个 Bot」，而是 **固定职责 + 固定输入输出格式**：

```text
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ 分析 Agent   │ →  │ 实现 Agent   │ →  │ 测试 Agent   │
│ 读需求/差异   │     │ 限定目录改码  │     │ 跑单测/快照   │
└─────────────┘     └─────────────┘     └─────────────┘
        ↓                   ↓                   ↓
              ┌─────────────────────────┐
              │  评审 Agent / 人工门     │
              │  diff 范围、安全、规范    │
              └─────────────────────────┘
```

| 角色 | SOP 要点 | 输出契约 |
|------|----------|----------|
| 分析 | 只读仓库；输出影响面、文件列表、风险点 | Markdown / JSON 任务卡 |
| 实现 | **仅允许改指定路径**；禁止改 lock、密钥 | Patch / 分支名 |
| 测试 | 跑约定命令；失败日志回传实现 Agent | 测试报告摘要 |
| 评审 | 对照 REGISTRY 规则、API 契约、i18n | 通过 / 驳回理由 |

**关键**：每个角色的 Prompt 里写清「不负责什么」，比写清「要做什么」更能防越权。

### 三、企业级 Prompt SOP 模板

```text
【角色】你是谁，负责什么，不负责什么
【目标】可验证的交付物（如：通过 CI 的 PR）
【上下文】允许读的目录、分支、文档版本
【约束】禁止编造接口；禁止未授权工具；禁止输出密钥
【流程】先读 REGISTRY → 再改码 → 再测 → 再自审
【输出】固定 JSON 或 PR 描述模板
【异常】资料不足拒答；测试失败附日志不瞎改
```

与业务 Agent 共用同一套 **防注入** 原则：用户输入、外部网页、上传文件均为不可信数据，不能覆盖系统指令。

### 四、工具权限矩阵（最小权限）

| 工具类别 | 默认权限 | 示例 |
|----------|----------|------|
| 读文档、读仓库 | 自动 | handbook、接口说明 |
| 静态分析、单测 | 自动或受控 | eslint、vitest |
| 改代码 | 路径白名单 | 仅 `src/features/foo` |
| 写库、发布、删文件 | **人工确认** | DDL、npm publish |

这和业务侧「审核 Agent」是同一套 **审批门（Approval Gate）** 思想：高风险行为不从模型自主闭环里走。

### 五、多编码 Agent 并行：何时用、何时不用

**适合并行**

- 多模块无依赖（i18n 文案、独立页面、文档同步）；
- 探索性 spike（多个子 Agent 试方案，人选一个）；
- CI 诊断 + 实现 Agent 分工（一个只读日志，一个只改修复）。

**必须串行**

- 同一文件的写冲突；
- 数据库迁移 + 业务代码依赖顺序；
- 接口契约先定再实现。

编排层用 **任务锁 / 文件锁 / 队列** 比指望模型「自觉别抢写」可靠。

### 六、团队资产库：让 Agent 可复用

把 Agent 能力沉淀成资产，而不是每人一套 Prompt：

| 资产类型 | 内容 | 作用 |
|----------|------|------|
| 规则 `.cursor/rules` | 技术栈、命名、禁止项 | 统一 Host 行为 |
| 技能 SKILL.md | 专项流程（PR、Canvas） | 按需加载 |
| REGISTRY.md | 工具/脚本/知识索引 | CI 校验、新人 onboarding |
| CLI + MCP | Figma/MasterGo 设计稿接入 | 设计 → 代码可追溯 |

可量化的成果包括：**入职培训周期缩短、UI 走查周期下降** — 比「我们用了 AI」更具体。

### 七、与 CI/CD 闭环

```text
PR 打开 → 代码扫描 Agent（只读评论）
       → 实现 Agent 修 CI（限定范围）
       → 人工 Approve 合并
```

原则：**Agent 插在现有 Git 流程里，而不是替代 Code Review。**

### 八、一条完整的工程链路

> 业务上 Agent 走服务端 Tool，密钥不进 Prompt；研发上 Cursor 子 Agent 走 MCP 读设计稿；团队用 REGISTRY + CI 校验 Prompt 资产，写操作过人工门。

这是前端架构 + 全栈 + 业务系统三条线交汇时，我比较推荐的落地方式。
